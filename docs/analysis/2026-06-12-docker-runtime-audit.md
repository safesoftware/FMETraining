# Docker Runtime Path / Permission / Env Audit

Status: DRAFT audit (uncommitted)
Date: 2026-06-12
Scope: breadth inventory of filesystem-path / writable-dir / env-var dependencies in `app/` + `pipeline/` + `worker.py` and whether each matches the Docker Compose runtime reality. (Architecture verdict is a separate agent's deliverable.)

## Summary

The Docker move split the old single-root layout (code+content+writable repo under one tree) into: code baked at `/app` (root-owned, mode 755), version content bind-mounted read-only at `/content`, `data/` bind-mounted read-only at `/app/data`, `artifacts/` bind-mounted read-write at `/app/artifacts`, `.cache` pre-created for `appuser` — all running as `appuser` (uid 10001). The **app layer** (`app/config.py`, `app/main.py`, `app/routes/*`, `app/services/pipeline_runner.py`) was taught this layout and reads `LESSON_CONTENT_ROOT` / `ARTIFACTS_ROOT` / `DRAFTS_ROOT` from settings. The **pipeline layer** (`pipeline/config.py`) was not: it still computes `REPO_ROOT = Path(__file__).parent.parent` (`=/app`) and hangs every directory and well-known-file path off it. The worker bridges the seam **only for step 1** (it passes `content_root` as `repo_root` into `build_manifest`) and **for artifacts** (it passes an explicit `output_dir`). Everything else in the pipeline layer that resolves a *lesson content* path or *writes outside artifacts* still uses `REPO_ROOT=/app`, where the version trees do not exist (`.dockerignore`) and which `appuser` cannot write. This is **one broad seam, not a handful of one-offs**: the same `REPO_ROOT`-vs-mount divergence reappears at every pipeline content read and every pipeline write that isn't artifacts. KNOW-2353 (step 5/6 lesson HTML) is the load-bearing instance; the rest are the same defect on opt-in / non-worker paths plus a couple of genuinely independent app-layer issues (`drafts_root` default, `.env` no-op).

Container evidence (live `fme-train-app`, healthy, `TASK_DISPATCHER=inprocess`):
- `ls -ld /app` → `drwxr-xr-x root root` — `appuser` **cannot** write `/app` root (`touch /app/_probe` → Permission denied).
- `/app/2025.1`, `/app/2026.1`, `/app/2024.0` → **No such file or directory** (version trees dockerignored). They exist only under `/content`.
- `/app/.cache` → `drwxrwxrwx appuser appuser` (writable; KNOW-2352 fix). `/app/artifacts` → 9p rw mount (writable). `/app/data` → 9p **ro** mount (`touch` → Read-only file system). `/content` → 9p ro mount.
- `/var/lib` → `root root 755`; `mkdir /var/lib/fme-train` → Permission denied.
- `/app/.env` → **absent** (dockerignored) → `pipeline/config.py` `load_dotenv` is a silent no-op in-container.
- `/app/data/jira_export.csv` → absent.
- Env present: `LESSON_CONTENT_ROOT=/content`, `ARTIFACTS_ROOT=/app/artifacts`, `TASK_DISPATCHER=inprocess`, no `DRAFTS_ROOT`.

## Notes by category

### Paths (content resolution — the seam)
The pipeline's content-path resolution is `config.REPO_ROOT / <relative lesson path>`. The manifest stores lesson paths as *relative* (`<version>/<lp>/<course>/<lesson>/index.html`, `pipeline/manifest.py:234,280`; `lesson_dir` derived at `assessment.py:305` as `Path(lesson["path"]).parent`). Step 1 resolves these against the injected `repo_root` (= `_content_root` = `/content`), so step 1 is correct. But the relative path / `lesson_dir` then travels in `manifest`/`recommendations` into steps 3 and 6, which re-resolve against `config.REPO_ROOT` (`=/app`) because `pipeline_runner` does not thread `content_root` into them (findings 2, 3). `/app/<version>` does not exist (dockerignored), so `edit_suggestions._build_prompt` logs `WARNING: lesson HTML not found at /app/<version>/...` and skips every lesson — the KNOW-2353 symptom. The same `REPO_ROOT`-relative content read recurs in `enrich_alt_text` (finding 9) and the Skilljar push/release writers (finding 8); those simply aren't on the worker's 6-step path, so they're latent rather than already-broken. The fix that resolves KNOW-2353 should be a single seam fix (give the pipeline a content root and an output root that the worker sets from `Settings`), not per-call patches — otherwise findings 8/9 resurface when those flows are wired into the web app.

### Permissions (writable dirs)
- `/app` root is root-owned 755 → `appuser` cannot create anything directly under `/app` that isn't a bind-mount or a pre-chowned dir. Confirmed by probe. This is why KNOW-2352 had to pre-create `/app/.cache`.
- Writable at runtime for `appuser`: `/app/.cache` (chowned), `/app/artifacts` (9p rw mount, uid 1000, world-writable bits), `/tmp` (probe OK — covers `tempfile` use in `lesson_image_upload.py:106`). 
- NOT writable: `/app` root, `/app/data` (ro mount; finding 7), `/content` (ro mount), `/var/lib/fme-train` (finding 4). 
- `drafts_root` (finding 4) is the most dangerous permission gap that isn't ticketed: the default points at an unprovisioned `/var/lib` path, `appuser` can't create it, and the route surfaces it as a 503 only on first draft write — so it passes a smoke test and fails the first time someone edits a lesson in the report.

### Env propagation (the core seam, restated concretely)
Compose injects env via `.env.compose` + `.env` + `environment:` blocks into the process. `app/config.py` (pydantic-settings) reads the container-aware vars: `lesson_content_root`, `artifacts_root`, `drafts_root`, `database_url`, `s3_*`, `task_dispatcher`. `pipeline/config.py` reads a *different, overlapping* set straight from `os.getenv` (`OPENAI_*`, `JIRA_*`, `AWS_*`, `SKILLJAR_*`, `APP_BASE_URL`) and derives **all directory paths from `REPO_ROOT`, reading none of `LESSON_CONTENT_ROOT` / `ARTIFACTS_ROOT` / `DRAFTS_ROOT`.** The worker (`worker.py:68` → `make_step_body()` with no args; `make_step_body` then reads `get_settings()` at `pipeline_runner.py:94-96`) is the *only* place that translates app settings into pipeline inputs, and it does so for exactly two things: `output_dir` (artifacts) and the step-1 `repo_root` (content). Any pipeline path that doesn't flow through one of those two injection points silently uses `REPO_ROOT=/app`. Net: the var the app honors but the pipeline ignores is `LESSON_CONTENT_ROOT` for steps 3/5/6 (and `enrich_alt_text`), which is precisely findings 2/3/9.

## Method note
All hypotheses confirmed against the live `fme-train-app` container with read-only probes (`ls -ld`, `touch && rm`, `mount`, `env`, existence checks). No code edited, no container mutated beyond ephemeral probe files (removed). `worker-runner` is profile-gated and not running; findings about worker steps are derived from the in-process dispatcher (`TASK_DISPATCHER=inprocess`), which runs the identical `make_step_body` path in the live app container.
